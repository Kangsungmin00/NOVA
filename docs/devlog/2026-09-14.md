# 2026-09-14

## Entity 상태 전이 구조 설계

NOVA-SIM에는 Simulation Time을 관리하는 `World`와 World 내부에 존재하는 `SpatialEntity`가 구현되어 있다.

현재 Entity는 다음과 같은 정적인 공간 상태를 가진다.

```text
SpatialEntity
├─ entity_id
├─ entity_type
├─ latitude
└─ longitude
```

World에서 `step()`을 실행하면 Simulation Time과 Tick은 변화하지만, Entity 자체의 상태는 아직 변하지 않는다.

이번 단계의 목표는 Entity가 시간에 따라 상태를 변화시킬 수 있는 구조를 설계하는 것이다.

---

## 1. 현재 구조의 한계

현재 World는 다음과 같은 형태로 동작한다.

```text
World
├─ Simulation Time
├─ Tick
└─ Entities
```

`World.step()`을 호출하면:

```text
Tick + 1
Simulation Time + 1 minute
```

이 발생한다.

그러나 Entity는 상태 변화 규칙을 가지고 있지 않다.

예를 들어 차량 Entity가 존재하여도 현재 구조에서는 다음과 같은 변화가 발생하지 않는다.

```text
Tick 0
Vehicle
position = A
status = IDLE

        ↓ World.step()

Tick 1
Vehicle
position = A
status = IDLE
```

시간은 흐르지만 공간 객체에는 변화가 없는 것이다.

따라서 NOVA-SIM을 실제 Simulation으로 확장하기 위해 Entity의 상태 전이가 필요하다.

---

## 2. Entity와 State 구분

Entity 자체와 Entity가 현재 가지고 있는 상태를 구분해서 생각하고자 한다.

예를 들어 `E001`이라는 Entity가 존재한다면:

```text
Entity
├─ Identity
│  └─ entity_id = E001
│
└─ State
   ├─ position
   ├─ status
   ├─ speed
   └─ destination
```

`entity_id`는 Entity가 존재하는 동안 유지되는 식별자이다.

반대로 다음 값은 Simulation 진행에 따라 변경될 수 있다.

```text
position
status
speed
destination
```

이러한 값을 Entity의 State로 본다.

개념적으로는 다음과 같이 정리할 수 있다.

```text
Entity
=
Identity
+
State
```

그러므로 `SpatialEntity`에서는 `latitude`, `longitude` 또한 Entity의 공간 상태에 해당한다.

---

## 3. 상태 전이

상태 전이는 단순히 변수 값을 변경하는 것과 구분할 필요가 있다.

예를 들어 다음 코드처럼 직접 값을 변경할 수도 있다.

```python
entity.status = "moving"
```

그러나 이 방식만 사용하면 상태가 왜 변경되었는지 표현하기 어렵다는 단점이 존재한다.

이에 상태 전이를 다음 구조로 바라보기로 했다.

```text
Current State
+
Condition / Action
+
Transition Rule
↓
Next State
```

예를 들어 이동하는 Entity의 상태를 다음과 같이 정의할 수 있다.

```text
IDLE
  │
  │ move
  ▼
MOVING
  │
  │ destination reached
  ▼
ARRIVED
```

상태 전이 표로 표현하면 다음과 같다.

| Current State | Condition / Action | Next State |
| ------------- | ------------------ | ---------- |
| `IDLE`        | 이동 시작              | `MOVING`   |
| `MOVING`      | 이동 중               | `MOVING`   |
| `MOVING`      | 목적지 도착             | `ARRIVED`  |

이 구조를 기반으로 가장 작은 상태 전이부터 구현하고자 한다.

---

## 4. Tick과 State Transition

현재 Tick 기반으로 Simulation Time을 진행한다.

따라서 Entity 상태 전이도 기본적으로 `World.step()`을 기준으로 발생하도록 설계할 예정이다.

```text
Tick 0

Entity
status = IDLE
position = 0

        ↓

World.step()

        ↓

Tick 1

Entity
status = MOVING
position = 1
```

이를 반복하면 다음과 같은 상태 변화가 만들어진다.

```text
Tick 0
IDLE
position = 0

    ↓

Tick 1
MOVING
position = 1

    ↓

Tick 2
MOVING
position = 2

    ↓

Tick 3
ARRIVED
position = 3
```

`World.step()`이 시간만 변경하는 역할을 가지고 있으나,  Entity의 상태 변화도 Simulation Tick과도 연결하고자 한다.

---

## 5. Entity 상태와 World 상태

Entity 상태는 Entity 자체의 정보만으로 결정되지 않을 수 있다.

차량의 이동은 다음과 같은 정보에 영향을 받을 수 있기 때문이다.

```text
Vehicle State
├─ position
├─ speed
└─ destination

World State
├─ road
├─ traffic
├─ weather
└─ other entities
```

따라서 장기적으로 Entity 상태 전이는 다음 구조가 될 수 있다.

```text
Entity State(t)
+
World State(t)
+
Transition Rule
↓
Entity State(t + 1)
```

현 단계에서는 World 환경이나 다른 Entity와의 상호작용까지 구현하지 않는다.

하나의 Entity가 독립적으로 상태를 변경할 수 있는 최소 구조를 만드는 것을 우선으로 한다.

---

## 6. 상태와 행동의 분리

State와 Behavior를 구분한다.

State는 Entity가 현재 가지고 있는 값이다.

```text
position
status
speed
destination
```

Behavior는 Entity가 어떤 행동을 선택할지 결정하는 규칙이다.

```text
목적지가 있으면 이동한다.
목적지에 도착하면 정지한다.
```

따라서 장기적으로는 다음과 같은 구조를 고려할 수 있다.

```text
Entity
   │
   ├─ State
   │
   └─ Behavior
          │
          ▼
       Action
          │
          ▼
   State Transition
```

그러나 현재 단계에서는 Behavior 계층을 별도로 구현하지 않는다.

State Transition 자체를 먼저 검증한 이후 필요하면 분리한다.

---

## 7. 업데이트 순서 문제

여러 Entity가 존재하게 되면 상태 변경 순서도 고려해야 한다.

예를 들어 A와 B가 같은 Tick에서 움직일 경우 다음과 같이 순차적으로 상태를 직접 변경하면 문제가 발생할 수 있다.

```text
A 상태 계산
↓
A 상태 변경
↓
B 상태 계산
```

이 경우 B는 같은 Tick에 존재하던 A의 상태가 아니라 이미 변경된 A의 상태를 관찰할 수 있다.

Entity 실행 순서에 따라 Simulation 결과가 달라질 가능성이 있다.

장기적으로는 다음과 같은 방식이 필요할 수 있다.

```text
Tick t State
    │
    ├─ A next state 계산
    ├─ B next state 계산
    └─ C next state 계산
            │
            ▼
       상태 일괄 적용
            │
            ▼
       Tick t + 1 State
```

첫 구현에서는 Entity 하나만 사용하므로 이 문제를 바로 해결하지 않는다.

대신 다중 Entity Simulation으로 확장할 때 반드시 다시 검토할 항목으로 남긴다.

---

## 8. 첫 구현 범위

처음부터 Person, Vehicle, Robot 등의 구체적인 Entity를 구현하지 않는다.

최소 Entity 하나를 대상으로 상태 전이를 구현하는 것을 목표로 한다.

```text
Entity E001

Tick 0
status = IDLE
position = 0

Tick 1
status = MOVING
position = 1

Tick 2
status = MOVING
position = 2

Tick 3
status = ARRIVED
position = 3
```

이를 통해 다음 사항을 확인한다.

* Entity가 자신의 현재 상태를 가진다.
* Tick에 따라 상태가 변경된다.
* 상태 변경이 `World.step()`과 연결된다.
* `World.get_state()`에서 변경된 Entity 상태를 확인할 수 있다.
* Observer에서도 변경된 상태를 확인할 수 있다.

---

## 9. 이번 단계에서 하지 않는 것

현재 단계에서는 다음 기능을 구현하지 않는다.

```text
다중 Entity 상호작용
경로 탐색
속도 및 가속도 모델
충돌 처리
Behavior Tree
Utility AI
Event System
State History 저장
실제 GIS Network 이동
```

가장 작은 상태 전이 구조를 검증하고자 하기 때문이다.

---

## 10. 다음 작업

다음 개발에서는 최소 State Transition을 코드로 구현한다.

예상 흐름은 다음과 같다.

```text
World.step()
    ↓
Entity Update
    ↓
Current State 확인
    ↓
Transition Rule 적용
    ↓
Next State 생성
    ↓
Entity State 변경
    ↓
World.get_state()
```

다음 질문을 검토한다.

1. Entity가 스스로 상태를 변경해야 하는가?
2. World가 Entity 상태를 변경해야 하는가?
3. 별도의 System이 상태 전이를 담당해야 하는가?
4. Current State와 Next State를 분리해야 하는가?
5. 상태 변화 기록을 언제부터 저장할 것인가?

구조를 과도하게 추상화하지 않고, 실제 동작을 확인한 뒤 필요한 책임을 분리한다.


---

## 정리

entity 구조는 가장 오래 고민했던 부분이다.

이번 단계에서 가장 중요하게 본 것은 Entity를 단순한 지도 위 객체가 아니라 **시간에 따라 상태가 변화하는 Simulation 객체**로 확장하는 것이다.

현재 구조:

```text
World
↓
Time
↓
Spatial Entity
```

다음 목표:

```text
World
↓
Time / Tick
↓
Entity
↓
State
↓
State Transition
↓
New State
```

이 상태 전이 구조를 먼저 검증한 후 Behavior, Event, State History 등의 구조를 단계적으로 추가할 예정이다.
