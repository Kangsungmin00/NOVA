# 2026-09-13 Devlog — NiceGUI 기반 Simulation Observer 구축

## 1. 목표

오늘의 목표는 전날 구현한 `World`를 Python 내부 객체로만 두지 않고, 시뮬레이션 상태를 외부에서 조회하고 브라우저에서 시각적으로 관측할 수 있는 구조를 만드는 것이었다.

구현 목표를 데이터 흐름으로 정의하면 다음과 같다.

```text
Scenario
   ↓
World
   ↓
get_state()
   ↓
Observer
   ↓
Renderer
   ↓
Leaflet
```

추가로 API를 통해서도 World 상태를 확인할 수 있도록 FastAPI 연결을 검증했다.

# 2. Python 프로젝트 구조 정리

기존 구조는 다음과 같았다.

```text
NOVA/
└─ src/
   └─ world.py
```

단일 Python 파일 구조에서는 의존성 관리와 패키지 import가 불명확해질 수 있기 때문에 `uv`를 사용해 Python 프로젝트 구조를 정리했다.

현재 구조는 다음과 같다.

```text
NOVA/
├─ pyproject.toml
├─ uv.lock
├─ .venv/
│
└─ src/
   └─ nova_sim/
      ├─ __init__.py
      ├─ world.py
      ├─ entity.py
      ├─ scenario.py
      ├─ renderer.py
      ├─ observer.py
      └─ api.py
```

Python package는 다음 경로에서 관리한다.

```text
src/nova_sim/
```

따라서 내부 모듈은 다음과 같이 import할 수 있다.

```python
from nova_sim.world import World
```

# 3. uv 기반 환경 관리

기존에는 별도의 `nova` 가상환경을 직접 생성했지만, 프로젝트 환경 관리를 `uv`로 통일했다.

```bash

```

패키지 설치는:


이를 통해 다음 파일이 Python 프로젝트 환경의 기준이 된다.

```text
pyproject.toml
uv.lock
```

목표는 Git 저장소를 다른 개발환경에 clone하더라도 동일한 dependency 구성을 복원할 수 있도록 하는 것이다.

# 4. FastAPI 기반 World API 검증

World 상태를 Python 프로세스 외부에서 조회할 수 있는지 확인하기 위해 FastAPI를 추가했다.

현재 구현한 endpoint는 다음 두 개다.

```text
GET  /api/world
POST /api/world/step
```

### GET `/api/world`

현재 World 상태를 반환한다.

코드적으로는:

```python
return world.get_state()
```

형태다.

### POST `/api/world/step`

World를 한 단계 진행시킨 뒤 새로운 상태를 반환한다.

```python
world.step()

return world.get_state()
```

Swagger UI를 통해 실제 요청을 수행했고:

```text
tick: 0
↓
POST /api/world/step
↓
tick: 1
```

변화를 확인했다.

이를 통해 다음 경로를 검증했다.

```text
Python Object
↓
get_state()
↓
FastAPI
↓
HTTP
↓
JSON
↓
Browser
```

현재 Observer에서는 FastAPI를 경유하지 않고 World를 직접 사용하고 있다.

FastAPI와 Observer에서 각각 별도의 `World()`를 생성할 경우 서로 다른 상태를 관리하게 되므로, 현 단계에서는 Observer 실행 시 FastAPI World와 상태를 공유하지 않는다.

향후에는 단일 Simulation Runtime을 두고 API와 Observer가 동일한 상태를 조회하는 구조가 필요하다.

# 7. UI State 갱신 구조

초기에는 `refresh()` 내부에서 직접:

```python
state = world.get_state()
```

를 다시 호출했다.

하지만 이 경우 STEP 처리 과정에서 상태를 반복 조회하게 됐다.

기존 흐름은 대략 다음과 같았다.

```text
step()
↓
get_state()
↓
refresh()
↓
get_state()
```

이를 수정해서 `refresh()`는 State 조회가 아니라 **State → UI 반영**만 담당하도록 변경했다.

현재 구조는:

```python
def refresh(state):
    ...
```

이며 STEP은:

```text
world.step()
↓
state = world.get_state()
↓
refresh(state)
```

형태다.

이를 통해 역할을 다음과 같이 분리했다.

```text
World
→ State 생성

Observer
→ State 소비

refresh()
→ State를 UI에 반영
```

# 8. Initial State와 Runtime State 구분

Observer 페이지 초기화 시에는 한 번 상태를 읽는다.

```python
initial_state = world.get_state()
```

이 상태는 현재 다음 용도로 사용한다.

```text
World Center
Initial Entity Rendering
Initial UI Values
```

STEP 이후에는 다시 현재 상태를 조회한다.

```python
world.step()
state = world.get_state()
```

따라서 현재 상태 조회 흐름은:

```text
Page Initialization
↓
initial_state

Runtime Step
↓
new state
```

로 구분되어 있다.

현재 `entities`는 초기 상태에서만 렌더링되므로, STEP 이후 Entity 좌표가 변해도 Marker가 자동으로 이동하지 않는 한계가 있다.

# 9. SpatialEntity 구현

World 내부에서 공간 객체를 표현하기 위한 최소 모델로 `SpatialEntity`를 추가했다.

현재 데이터 모델은 다음과 같다.

```text
SpatialEntity
├─ entity_id
├─ entity_type
├─ latitude
└─ longitude
```

예상 상태 표현은 다음 형태다.

```python
{
    "entity_id": "agent_001",
    "entity_type": "agent",
    "latitude": 37.5665,
    "longitude": 126.9780,
}
```

현재는 `Agent`, `Vehicle`, `Robot`을 개별 클래스로 구현하지 않고 하나의 일반 SpatialEntity로 시각화 파이프라인을 우선 검증하고 있다.

# 10. Entity Registry

World 내부에는 Entity를 관리하기 위한 collection을 추가했다.

현재 개념은 다음과 같다.

```text
World
└─ entities
    ├─ entity_001
    ├─ entity_002
    └─ ...
```

Entity는 다음 메서드를 통해 등록한다.

```python
world.add_entity(entity)
```

그리고 `get_state()`에서는 Entity 내부 객체를 그대로 외부에 노출하지 않고 상태 representation으로 변환한다.

```text
Entity Object
↓
entity.get_state()
↓
dict
↓
World.get_state()
```

따라서 현재 World State에는 다음 정보가 포함된다.

```text
world_id
current_time
tick
seed
world_center
entities[]
```

# 12. World Center 상태 추가

Leaflet 초기 구현에서는 지도 중심 좌표가 Observer에 하드코딩되어 있었다.

```python
center=(37.5665, 126.9780)
```

이 경우 Observer가 특정 시나리오의 공간 위치를 알고 있어야 한다.

이를 제거하기 위해 World State에 `world_center`를 추가했다.

예:

```python
"world_center": {
    "latitude": ...,
    "longitude": ...
}
```

Scenario가 초기 중심 좌표를 결정하고:

```text
Scenario
↓
World
↓
get_state()
↓
world_center
↓
Observer
```

형태로 전달한다.

Observer에서는:

```python
world_center = initial_state["world_center"]
```

를 사용해 지도를 초기화한다.

현재 `zoom=13`은 Observer 표현 설정으로 남겨두었다.

# 14. Leaflet Custom Marker 문제

기본 Leaflet Marker는 파란색 Pin으로 표시됐다.

Entity Type 기반 아이콘을 사용하기 위해 `L.divIcon()`으로 변경하려 했으나 초기 구현에서는 기본 Marker가 계속 출력됐다.

최종적으로 동작한 코드는 다음과 같다.

```python
marker.run_method(
    ":setIcon",
    f'window.L.divIcon({{html: "{icon}", className: ""}})'
)
```

핵심은 browser global object에 등록된 Leaflet 객체를 명시적으로 사용하는 것이었다.

```javascript
window.L.divIcon(...)
```

이를 통해:

```text
agent      → 📍
vehicle    → 🚚
robot      → 🤖
warehouse  → 🏭
```

형태의 custom marker를 출력할 수 있게 됐다.

이 과정에서 Python/NiceGUI와 Client-side JavaScript 사이의 경계를 확인할 수 있었다.

# 15. async Page 초기화

Leaflet은 Client-side에서 초기화되기 때문에 지도 초기화 완료 시점과 Marker 조작 시점을 구분할 필요가 있었다.

Observer 페이지는 다음 구조를 사용한다.

```python
@ui.page('/')
async def main():
```

지도 생성 이후:

```python
await world_map.initialized()
```

를 통해 Leaflet 초기화 완료를 기다린 뒤 초기 Entity 렌더링을 실행한다.

구조는:

```text
NiceGUI Page 생성
↓
Leaflet 생성 요청
↓
await world_map.initialized()
↓
Leaflet 준비 완료
↓
Entity Rendering
```

이다.

현재 Custom Marker 문제의 직접 원인은 JavaScript expression 쪽이었지만, Leaflet Client 객체를 조작할 때 초기화 시점을 관리할 수 있도록 async 구조는 유지했다.

# 17. 파일별 책임

현재 모듈별 역할은 다음과 같이 정의했다.

| Module        | Responsibility                 |
| ------------- | ------------------------------ |

# 19. 현재 한계

현재 Observer는 World 상태를 시각적으로 확인할 수 있지만 실시간 Simulation Viewer 수준은 아니다.

가장 큰 제약은 다음과 같다.

### Entity는 초기 렌더링만 수행

```python
for entity in initial_state["entities"]:
    render_entity(...)
```

따라서 STEP 이후:

```text
Entity latitude 변경
Entity longitude 변경
```

이 발생하더라도 기존 Marker의 위치는 변하지 않는다.

### Renderer는 Point Marker만 지원

현재 `SpatialEntity`는 latitude/longitude 기반 Point만 지원한다.

다음 Geometry는 아직 지원하지 않는다.

```text
Line
Polygon
Grid
Network
```

### Event Log는 실제 Event System이 아님

현재:

```text
Tick N completed
```

문자열을 UI에서 직접 생성한다.

향후에는 World 또는 Event Engine에서 발생한 실제 Event를 받아야 한다.

# 20. 다음 구현 목표

다음 단계의 핵심은 **Runtime Entity State와 Leaflet Layer를 연결하는 것**이다.

목표 데이터 흐름은 다음과 같다.

```text
STEP
↓

Entity State Change
↓
```

이를 위해 Observer 또는 Renderer에서 다음 매핑이 필요할 가능성이 있다.


```python
    "vehicle_001": marker,
}
```

형태가 될 수 있다.

이 구조가 구현되면 Entity가 생성될 때마다 Marker를 새로 그리는 대신 기존 Layer를 찾아 상태를 갱신할 수 있다.
